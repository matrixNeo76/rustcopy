You work on `robocopy-ingest-cli`'s performance measurement tooling. This project already has a working, report-driven benchmarking pipeline — your job is to use and extend it, not invent a parallel one.

## The existing pipeline (use this, don't replace it)

- `scripts/benchmark-threads.ps1` compares `--threads` (`/MT`) values by running the real `target\release\robocopy_ingest.exe` and reading timing/throughput back from each run's own `--report-path` JSON (`phase_timing`, `robocopy_transfer.elapsed_seconds`/`throughput_mbps`/`files_copied`). It always runs the first thread value twice — once as an unmeasured warm-up, once measured — because what matters for a scheduled incremental job is the **steady-state** case (destination already aligned, robocopy mostly re-scanning and skipping), and a cold run against a misaligned destination would swamp that signal with pure copy time.
- `scripts/analyze-runs.ps1` reads every `--report-path` JSON under a directory (recursively with `-Recurse`) and prints a trend table: files copied, throughput, total vs. robocopy-only time, wrapper overhead. It is pure parsing of the existing report schema (`report.rs`'s `PhaseTiming`/`TransferReport`) — no new capture format.
- Results live under `_ops_reports\benchmark\` (gitignored, like the pre-existing `_ops_reports\`), one JSON per run, named so `analyze-runs.ps1 -ReportsDir _ops_reports\benchmark -Recurse` can pick them all up later. This is about the **detailed** JSON report specifically, not history in general: `history.rs`'s `RunHistory` already appends a compact NDJSON line per run to `.rustcopy_history.jsonl` beside `--report-path`, but that line is deliberately aggregate-only (timings/throughput/exit code, no per-file detail) — it is not a substitute for keeping the full reports a benchmark sweep actually needs to compare. A shared/fixed `--report-path` still gets overwritten on every run, which is what a unique path per run avoids; don't benchmark against one.
- Real-world scale references already exist and should be reused rather than re-derived: `_ops_reports/claude-code_*` logs document actual production runs (one full-profile run at 1.34M files, 356 MB at `debug` log level vs. `info` — D18), and `generations.rs`'s `#[ignore]`d `probe_manifest_size_at_real_world_scale`/`probe_manifest_ram_at_real_world_scale` model their synthetic file counts/path shapes directly on `_ops_reports/claude-code_dest2-qnap-datas01_20260805_153728.log`'s real nested `node_modules` trees, not an arbitrary guess. Follow that same pattern — ground new synthetic fixtures in a real captured `_ops_reports` log, cite which one, don't invent plausible-sounding numbers.

## Directives

- **Do not propose `typeperf`, `RAMMap`, or Windows performance-counter tooling.** Nothing in this project's benchmarking currently touches OS-level counters; the entire pipeline is deliberately black-box against rustcopy's own `--report-path` JSON, which already carries phase timing and throughput. Adding a second, counter-based measurement path would fork the pipeline `analyze-runs.ps1` is built to unify.
- A benchmark run needs the **release** binary (`cargo build --release`), never debug — `benchmark-threads.ps1` already checks for `target\release\robocopy_ingest.exe` and refuses to run without it; don't silently fall back to a debug build, which would produce numbers nobody should compare against a release baseline.
- When comparing an engine or flag change (not just `--threads`), extend `benchmark-threads.ps1`'s pattern (`Invoke-TimedRun`, warm-up-then-measured, unique `--report-path` per run under `_ops_reports\benchmark\`) rather than writing a standalone one-off script — `analyze-runs.ps1` only produces a useful trend if every benchmark script feeds it comparable report shapes in the same directory convention.
- `#[ignore]`d probe tests (the two `generations.rs` examples above) are one-off measurements, not per-run regression tests — don't remove their `#[ignore]` to "add coverage"; they allocate millions of entries and are meant to be run deliberately, not on every `cargo test`.
- A synthetic dataset generator (many small files, deep nesting) belongs in `scripts/`, PowerShell, matching the existing scripts' style (param block, `$ErrorActionPreference = "Stop"`, `_ops_reports`-relative output) — not a new Rust binary, unless the generator itself needs to exercise rustcopy's own scanning code paths directly.
- Report a regression in the same units this pipeline already reports in: files/sec, MB/s, wall-clock phase seconds (`inventory`/`transfer`/`verification`/`baseline`) from `phase_timing` — not raw CPU/memory counters this project doesn't currently collect.

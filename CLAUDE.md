# CLAUDE.md — Claude Code & AI Agent Prompt Instructions

This file contains specific context, conventions, and operational instructions for Claude Code and AI assistant agents working on `robocopy-ingest-cli` (`rustcopy`).

## 1. Quick Reference & Commands

- **Build Project**: `rtk cargo build` or `cargo build`
- **Build Release**: `rtk cargo build --release` or `cargo build --release`
- **Run Full Test Suite**: `rtk cargo test` (ALWAYS prefer `rtk cargo test` for token optimization)
- **Run Specific Test**: `rtk cargo test <test_name>`
- **Check Compilation**: `rtk cargo check`
- **Summarize Module Impact**: `rtk smart <file>`
- **Query Code Graph**: `graphify query "<question>" --graph src/graphify-out/graph.json`

## 2. Key Architecture Concepts for Claude

When editing or extending `robocopy-ingest-cli`, keep these design patterns in mind:

### Robocopy Process Execution:
- The actual execution goes through the `CommandRunner` trait (`src/engine/robocopy.rs`).
- `ProcessRunner` is used on Windows (`#[cfg(windows)]`), while `ScriptedRunner` is used in unit tests on all OSes.
- Never modify Robocopy flag building without updating the corresponding unit tests in `robocopy::tests`.

### Memory Safety & Anti-OOM Controls:
- **Logging**: Uses `tokio::sync::mpsc::channel(10_000)` with `try_send`. Never switch back to an `unbounded_channel`.
- **Integrity Report Capping**: `IntegrityCheck` caps error vectors at `MAX_REPORTED_ERRORS = 10_000`.

### CLI Argument Rules:
- All CLI flags defined in `src/cli.rs` must also support optional TOML config overrides via `src/config.rs` (`IngestConfig`). `merge_config` only overwrites a field when the CLI still holds clap's own default for it (see the comment in `Args::merge_config`); it cannot yet distinguish "explicit CLI value equal to the default" from "no CLI value at all" (would need `ArgMatches::value_source`).
- Paths should be normalized via `normalize_path_arg` to handle Windows backslashes correctly.
- Default pattern is `*` for full recursive copy. `--mirror` mode runs `check_mirror_safety` in `main.rs`, which diffs the destination tree against the source inventory and aborts (dedicated exit code 3) unless `--force-purge` is given or the run is interactive and the operator confirms. This only works when a full prescan was taken; `--no-prescan` + `--mirror` always requires `--force-purge`.
- Stdout/stderr decoding uses `src/oem_codec.rs` (a hardcoded CP850 table plus a `GetOEMCP()` runtime check), **not** `encoding_rs::Encoding::for_label(b"ibm850")` — `encoding_rs` does not implement single-byte DOS/OEM code pages, so `for_label(b"ibm850")` always returns `None` and silently falls back to UTF-8. Do not reintroduce that pattern.
- `--enable-dedup`, `--cloud-sync-target`, `--install-service` are accepted for forward compatibility but are **not implemented** (see `[NOT IMPLEMENTED]` markers in `src/cli.rs`). Don't describe these as working features in docs.
- `--ignore-transient-missing` (F26a, closes half of D2) **is implemented**: `integrity::ignore_transient_missing()` runs after `--verify-integrity` and drops `missing_in_dest`/`unreadable` entries matching well-known transient patterns (`.log`, `.tmp`, anything under `.git/objects/`), recomputing `status`. Has no effect without `--verify-integrity`. Do not confuse this with `--fast-verify` above — they're unrelated despite both touching the verification path.
- `--exclude-junctions` (F26d, closes D7) maps to robocopy's `/XJ` in `engine/robocopy.rs::build_args`. Without it, robocopy follows junction points/symlinked directories (its own default) — and so does the prescan: `scan::scan`/`scan::inventory`/`scan::directory_size` all take an explicit `follow_links: bool` parameter, driven from `!args.exclude_junctions` (or `!request.exclude_junctions` in the naive engine) at every call site in `main.rs`. Keep these two in sync — the whole point of the flag was that the prescan and the actual transfer used to walk different trees. `WalkDir` rejects cycles when following links, so a self-referencing junction errors per-entry instead of recursing forever.
- `--serve-dashboard` and its backing `src/server.rs` mock were **removed** (Release 5.4.0) in favor of the `notify-server` binary. Do not reintroduce a `--serve-dashboard` flag.
- `notify-server` (`src/bin/notify_server.rs`, `src/notify_server.rs`, `src/notify_sink.rs`) receives `--webhook-url` POSTs and fans them out to configurable channels. It is a **separate, feature-gated binary** (`--features notify-server`): axum must never become a default dependency of the main `robocopy_ingest` binary. `src/notify_sink.rs` (the `NotificationSink` trait and channel impls) has no axum dependency and is always compiled/tested; only `src/notify_server.rs` (the axum `Router`) and the bin are feature-gated.
- `--encrypt-aes256 <KEY>` / `--decrypt <KEY>` perform real streaming AES-256-GCM (see `src/crypto.rs`, fixed F25a/F25b, closes D3/D4). Encryption/decryption happen in fixed **1 MiB chunks** (`CryptoManager::encrypt_stream`/`decrypt_stream`), each with a fresh random nonce and an explicit length prefix — peak memory is O(chunk size), not O(file size), so this no longer OOMs on large files. On-disk format: `RCE1` magic header + repeated `nonce(12) || len(4, LE u32) || ciphertext+tag` records. `CryptoManager::encrypt_file`/`decrypt_file` write to a sibling temp file and `rename` atomically only on success — never leaves a half-transformed file at the real path. Both flags are mutually exclusive (`Args::validate()` rejects both being set, checked *before* the restore-mode early return since `--decrypt` is meant to be used with `--restore-from`). Do not reintroduce whole-file `std::fs::read`/`std::fs::write` for either direction.
- `--restore-from` is **fixed and verified (F24, closes D1)**: `--source`/`--dest` are now `Option<PathBuf>` with `required_unless_present = "restore_from"` (the previous `PathBuf` + `default_value = ""` combination silently made clap treat the arg as unconditionally required — an empty-string default is treated as "no default" by clap, so `required_unless_present` never took effect). Access them via `Args::source()`/`Args::dest()` (`&Path`, panics if called when neither was supplied — an invariant clap enforces before `validate()`/these accessors ever run in a real invocation), never the raw `Option` fields directly outside `cli.rs`. Covered by a black-box test that runs the compiled binary (`tests/cli_smoke.rs::restore_from_runs_end_to_end_without_source_or_dest`), not just `build_restore_args()` in isolation — the latter is exactly what let the original bug ship undetected.
- `restore::build_restore_args` takes the **original, already-parsed `Args`** for the current invocation and clones it, overriding only the fields that must come from the backup report (source/dest reversed, pattern, threads, retries, retry_wait_seconds, verify_integrity). Do not rewrite it to build a fresh `Args` via `try_parse_from` again — that was the F25b regression: every other flag typed alongside `--restore-from` (notably `--decrypt`, but also a custom `--log-path`/`--report-path`/`--webhook-url`) got silently discarded because `main.rs` replaces `args` wholesale with this function's return value. Caught only by a black-box test that combined `--restore-from` with `--decrypt` end-to-end, not by the pre-existing unit test (which never passed any extra flag).
- `check_mirror_safety` in `main.rs` is `async fn` (F26b, closes D5): the destination walk it does runs inside `tokio::task::spawn_blocking`, like every other blocking filesystem operation in that file (inventory, transfer, verify, crypto, the dest poller). Don't call it synchronously from `execute()` again — that's exactly the regression it fixed (froze the tokio executor, and `Ctrl+C` handling with it, for the whole scan on large trees).
- `report::SCHEMA_VERSION` is `2` (F26c, closes D6): bumped from `1` after a past release renamed `integrity::Mismatch`'s fields (`source_sha256`/`dest_sha256` → `kind`/`algorithm`/`source_digest`/`dest_digest`) without bumping it. Those four fields carry `#[serde(default)]` (with a dedicated `impl Default for MismatchKind`, documented as a deserialization fallback only) so a genuinely old-format report — which `restore::build_restore_args` parses in full — stays deserializable instead of failing `--restore-from` outright. `path` has no default; without it there's nothing to identify the entry by.
- `--log-level`/`--quiet`/`--log-max-bytes`/`--log-max-backups` (F27, closes D9) are implemented: `Args::log_config()` builds a `logging::LogConfig` (filter string + rotation settings) consumed by `logging::init`/`init_scoped`. `RUST_LOG` still wins over the CLI-derived filter, unchanged from before this existed. Rotation (`logging::rotate_if_needed`) runs once at startup, before the log file is opened — it is not a rolling/live rotation during the run. `--quiet` and `--log-level` are `conflicts_with` each other in clap (mutually exclusive, not "one silently wins").
- `--fast-verify` (F28, closes the other half of D2) **is implemented**, but deliberately *not* the way the original ROADMAP wording described ("hash only files robocopy declares copied"): the robocopy stdout parser (`engine::robocopy::parse_file_bytes`) extracts byte counts per line, not filenames, and is already load-bearing for progress reporting — reworking it to expose per-file identity was judged materially riskier than the alternative actually implemented: `cache.rs`'s `IngestCache`, keyed on **source** file size+mtime, persisted at `<dest>/.ingest_cache` (`cache::default_cache_path`). A file is skipped only when its current size+mtime match the entry from the *last run that verified it clean* — a file that fails verification is never written to the cache, so it keeps being re-checked every subsequent run until it actually passes (see `main.rs::verify`'s `failed` set, computed *before* `--ignore-transient-missing` runs, so a forgiven transient-missing file still isn't wrongly cached as confirmed-present). Known limitation, documented in the flag's own help text: this trusts the *source*'s identity, not a re-check of the destination's bytes — independent destination corruption (e.g. bit rot) with an unchanged source will not be caught on a run where that file gets skipped. `IntegrityCheck::skipped_unchanged` reports how many files were skipped this way (`0` when `--fast-verify` isn't used).
- `IntegrityCheck::skipped_unchanged`, `ScannedFile::modified_timestamp`, `HashAlgorithm::Xxh3` and `EXIT_INTEGRITY_FAILED = 4` (F28/F29a/F29b) are all additions on top of the F26c-era shapes; none of them break deserialization of older reports (all `#[serde(default)]` where relevant).
- Exit codes (`main.rs`): `0` success, `1` the transfer itself failed (robocopy exhausted retries on some item), `2` usage/unrecoverable error, `3` `--mirror` purge aborted, `4` the transfer succeeded but `--verify-integrity` found a problem (F29b, distinguishes "data never landed" from "data landed but doesn't match" for schedulers), `5` `--keep-generations` retention purge aborted (F35 — kept distinct from `3` so a scheduler can tell a mirror-purge abort from a retention-purge abort). `run()` in `main.rs` returns the exit code (`u8`) directly rather than a `bool`; `RunOutcome::exit_code` is computed once in `execute()`.
- `--hash-algo` has a third option, `xxh3` (F29a, via the `xxhash-rust` crate). It is **not cryptographic** — good for corruption detection, not for a backup where an attacker could have tampered with data. Don't recommend it for that use case in docs or generated summaries.
- `engine::CopyRequestBuilder`/`CopyRequest::builder()`, `IngestError::IntegrityFailed`, and `report::seconds()` were **removed** (F29c, closes D8) — they had zero callers. Do not reintroduce a builder pattern for `CopyRequest` without a real caller driving the requirement.
- `--vss-snapshot` (F30, closes O1) shells out to `vssadmin.exe` (`src/vss.rs`) rather than binding the VSS COM API directly — matches how the rest of the crate delegates to native tools instead of pulling in a COM/FFI dependency. `main.rs`'s `VssGuard` holds the shadow copy for the run and deletes it in a **synchronous `Drop`**, deliberately not an async cleanup step: `run()`'s `tokio::select!` drops `execute()`'s future outright on Ctrl+C instead of driving it to completion, and a `Drop` impl on a value still living in that future's local scope is the only thing guaranteed to still run when that happens. Never move a `VssGuard` into a `spawn_blocking` closure — that would detach it from the future and defeat this. Requires Administrator; fails clearly, never falls back to reading the live volume silently. `inventory_source`/`transfer`/`baseline`/`verify` all take an `effective_source: &Path` parameter (the shadow-remapped path when `--vss-snapshot` is active, `args.source()` otherwise) — `args` itself is never mutated, so the JSON report still shows the real source path. **Not tested end-to-end**: creating/deleting a real shadow copy needs real Administrator elevation and touches real system state, outside every other test's `tempdir`-only sandbox — only the pure parsing/path-remapping logic in `vss.rs` is unit-tested (6 tests, against real captured `vssadmin` output).
- `--resume-from <checkpoint>` (F31, closes O5) is **not** mid-file resume — `engine::robocopy::build_args` still never passes `/Z`, deliberately, for its throughput cost on small files (see the `/Z` note above). It relies on robocopy's own default of skipping a destination file whose size+timestamp already match the source. What it actually adds: `run()`'s `Ctrl+C` branch now writes a `checkpoint::Checkpoint` to `<report_path>.checkpoint.json` before returning (previously wrote nothing at all), and `checkpoint::build_resume_args` reconstructs `Args` from it the same way `restore::build_restore_args` does — clone the **original, already-parsed** `Args` for this invocation and override only source/dest/pattern/threads/retries/retry_wait_seconds/verify_integrity, so every other flag typed alongside `--resume-from` survives. Unlike `--restore-from`, source/dest are **not** reversed. `--restore-from` and `--resume-from` are `conflicts_with` each other in clap.
- `[[jobs]]` in the TOML config (F33, closes O10) lets one config file describe several independent backup jobs. `config::JobConfig` mirrors `IngestConfig`'s per-job fields plus `name`; `IngestConfig` is now `{ defaults: JobConfig, jobs: Option<Vec<JobConfig>> }` via `#[serde(flatten)]` on `defaults` — the top-level TOML fields are unchanged syntactically, only their representation moved. `JobConfig::merged_over(&self, base)` resolves one job against the file's top-level defaults (job wins on every field, whole-value overwrite — no list "extend" semantics for `exclude_files`/`exclude_dirs`, unlike CLI+config merging). `main.rs::run_jobs` runs every job **sequentially in one process**: each job's `Args` is rebuilt from a fresh clone of the *original* CLI invocation (never the previous job's already-merged `Args`), same discipline as `restore::build_restore_args`/`checkpoint::build_resume_args` — see the F25b note above for why rebuilding via `try_parse_from` instead would silently drop flags. A job that fails validation (e.g. missing source/dest) is reported and skipped, not fatal to the batch; `Ctrl+C` aborts the *remaining* jobs (the interrupted one still gets its checkpoint, as always). All jobs in a batch share **one log file**: `logging::init` only installs the global `tracing` subscriber on its first call per process (see its own doc comment) — a per-job `log_path` would silently have no effect past the first job, so `run_jobs` deliberately initialises logging once, from the file's top-level defaults. Each job still gets its **own** report: if a job doesn't set its own `report_path`, `main.rs::namespaced_path` inserts `.{job_name}` before the extension so jobs can't silently clobber each other's report — check the job's *own* `JobConfig.report_path` for this (`is_none()`), not the already-`merged_over`-resolved one, which always looks "set" once the file has a top-level default. Fixed as a side effect: `--source`/`--dest` were missing from `required_unless_present_any` for `--config`, so even pre-F33 single-job config-file mode could never actually be invoked without also passing dummy `--source`/`--dest` on the CLI — clap now also accepts `--config` alone; `Args::validate()` now explicitly checks `self.source.is_none() || self.dest.is_none()` before calling the panicking `Args::source()`/`dest()` accessors, since clap can no longer guarantee that invariant once `--config` is in the picture.
- `--backup-type <full|incremental|differential>` (F34, closes Cobian parity's central gap, now including the differential variant) is implemented in `src/generations.rs` + a dedicated `main.rs::execute_generation_backup` path, opt-in only — `None` (the default) is the exact pre-F34 plain-sync behaviour, nothing about the existing single-destination flow changed. Each run writes into a new `<dest>/<timestamp>_<type>/` subfolder and appends to `<dest>/.rustcopy_generations.json` (`GenerationManifest`); every recorded `Generation` stores the **full** source inventory (size+mtime per relative path) at the time it ran, not just the files actually copied — that's what lets the *next* incremental/differential diff against a complete picture instead of accumulating drift across a chain of partial deltas. `generations::changed_since` does the size+mtime diff (same trust model as `IngestCache`/F28 — not a hash re-check). `Incremental` diffs against `GenerationManifest::latest()` (the most recently recorded generation, of *any* type — so it chains, and each incremental only ever needs to know the delta since the previous run). `Differential` diffs against `GenerationManifest::latest_full()` (the most recent `Full` generation specifically, skipping over any `Incremental`/`Differential` in between) — so every differential run compares against the *same* reference point regardless of how many differentials ran since the last full, unlike `Incremental`. `execute_generation_backup` returns a clear error (not a silent full-copy fallback) if `Incremental` finds no prior generation at all, or if `Differential` finds no prior `Full` generation (an intervening `Incremental` does not count as the reference for `Differential`). **Deviation, documented in `ROADMAP.md` F34's row**: incremental/differential generations do **not** go through `transfer()`/robocopy — robocopy's file-selection arguments match filenames uniformly at every directory level it walks, there's no way to hand it an explicit list of specific relative paths to copy and nothing else. `engine::naive::copy_selected` (extracted from `NaiveCopyEngine::copy` via a shared `copy_files` helper — same per-file streaming `copy_one`, just fed an explicit slice of `ScannedFile` instead of doing its own pattern-driven scan) does the actual copy for all three types. `Args::validate()` rejects `--backup-type` together with `--mirror` (`IngestError::BackupTypeAndMirrorConflict`) — `/MIR`'s "purge anything not in source" has no coherent meaning against a destination that holds a manifest plus multiple generation subfolders. **Scope not yet wired up** (opt-in flag exists, not fundamentally incompatible, just future work): `--compare-baseline`, `--verify-integrity`, encrypt/decrypt, VSS remap of the destination side — none of these run inside `execute_generation_backup`.
- `--keep-generations <N>` (F35, closes retention/rotation) requires `--backup-type` (`IngestError::KeepGenerationsWithoutBackupType` if given without it — nothing to rotate without a generation history) and rotates by **cycle**, not by raw generation: `GenerationManifest::cycles()` groups the manifest's generations at every `Full` boundary (a cycle = one `Full` plus every `Incremental`/`Differential` that follows it, up to the next `Full`), and `generations_to_prune(keep_cycles)` returns the ids of every generation in a cycle older than the `keep_cycles` most recent ones. **Architectural decision made via `AskUserQuestion` before implementing** (same discipline as F34's generation-folder-vs-manifest choice): rotating per raw generation was rejected because it could delete a `Full` still referenced by a kept `Incremental`/`Differential`, orphaning that chain's ability to restore. `main.rs::prune_old_generations` does the actual deletion, gated by the same `--force-purge`/interactive-confirmation pattern as `check_mirror_safety` (that reuse was also confirmed via `AskUserQuestion` rather than assumed) — non-interactive + no `--force-purge` aborts with `IngestError::RetentionPurgeAborted`, mapped to a **new dedicated exit code `5`** (kept distinct from `--mirror`'s `3` so a scheduler can tell which kind of purge was aborted). **Ordering detail that matters**: pruning runs *after* the new generation has already been copied and saved to the manifest, so an aborted purge never loses the run's own backup — only the *rotation* of older cycles is rolled back, leaving one extra cycle on disk until the operator re-runs with confirmation. Runs inside `tokio::task::spawn_blocking` like every other blocking filesystem operation in `main.rs`. `keep_generations` has TOML parity in `JobConfig`/`IngestConfig` like `backup_type`; `force_purge` deliberately does **not** (same reasoning as the `--decrypt`/`--restore-from`/`--vss-snapshot`/`--resume-from` exceptions noted above — a purge-confirmation bypass shouldn't be silently settable from a config file).
- `--pre-command <CMD>`/`--post-command <CMD>` (F39, closes Cobian's "events" parity) are implemented in `src/hooks.rs`, run via `cmd /C` on Windows and `sh -c` elsewhere — deliberately cross-platform (unlike most of the crate's real-transfer paths) so `hooks.rs`'s own unit tests run on every CI platform, not just Windows. `run_pre_command` runs at the very top of `execute()`, before even the VSS snapshot (F30) — a pre-command's typical job is "stop the database so its files are consistent," which has to happen before a snapshot is taken, not just before the copy — and fails the whole run (`IngestError::PreCommandFailed`, non-transient, surfaces as exit code 2) if the command exits non-zero or can't be spawned at all: proceeding after a pre-command failure (e.g. a database that didn't actually stop) would silently back up inconsistent data. `run_post_command` runs near the end of **both** pipelines — the plain-sync tail of `execute()` and `execute_generation_backup`'s tail — after the backup has already succeeded, and unlike the pre-command a failure here does **not** fail the run (mirrors the existing `webhook_error` non-fatal pattern): it's only logged and recorded in the new `IngestReport::post_command_error` field, since retroactively failing an already-successful backup because its cleanup step broke would be worse than just flagging it. Both commands are plain strings (whatever `--pre-command`/`--post-command` or the TOML config gave, verbatim) — same trust boundary as `--webhook-url`: entirely operator-supplied, not attacker-controlled input, so `hooks.rs` does no escaping/sandboxing. Both are blocking (`Command::status()` waits for the child), so both call sites wrap them in `tokio::task::spawn_blocking` like every other blocking operation in `main.rs`. `pre_command`/`post_command` have TOML parity in `JobConfig`/`IngestConfig`.
- `--install-schedule <SPEC>`/`--schedule-name <NAME>`/`--uninstall-schedule <NAME>` (F36, closes scheduler parity) are implemented in `src/schedule.rs`, shelling to `schtasks.exe` — same "delegate to a native tool" pattern as `vss.rs`/`vssadmin.exe` (F30), deliberately **not** an internal scheduler process. **Architectural decision made via `AskUserQuestion` before implementing**: this decouples F36 from F37 (the real Windows service) entirely — a scheduled job is just a Task Scheduler entry that re-invokes this same binary later, so no persistent process of this crate's own is ever running while waiting for the next trigger. `SPEC` accepts a small, fixed grammar (`ScheduleSpec::Daily`/`Hourly`/`Weekly`, parsed by `parse_schedule_spec`) — `daily@HH:MM`, `hourly@N`, `weekly@DAY,...@HH:MM` — not a general cron expression, kept deliberately narrow for a first cut. The command Task Scheduler will run (`/TR`) is built from the **real** `std::env::args()` of the current invocation, not a synthetic re-serialization of the parsed `Args` struct: `strip_schedule_flags` removes only the three scheduling flags themselves (both `--flag value` and `--flag=value` forms), so whatever else was typed alongside `--install-schedule` (including `--config job.toml`) survives verbatim into the scheduled command — a `--config`-based invocation gets its config file re-read on every scheduled run, not frozen at install time. `build_task_run_command` quotes only the tokens that need it (contain whitespace), matching Windows command-line conventions. `--uninstall-schedule` is a pure removal operation: exempted from `--source`/`--dest`'s `required_unless_present_any` and intercepted at the very top of `main.rs::run()`, before even the `--restore-from`/`--resume-from`/`--config` branch — no backup invocation needs to validate for a task deletion. `--install-schedule` runs the opposite way: **after** `Args::validate()` succeeds, since installing a schedule is only useful for a genuinely runnable invocation. `--install-schedule`/`--uninstall-schedule`/`--restore-from`/`--resume-from` are pairwise `conflicts_with_all` in clap. **Known gap, documented in the flag's own help text and `ROADMAP.md`'s F36 row**: no `--list-schedules` in this first cut — parsing `schtasks /Query`'s output reliably was judged out of scope for a v1; the operator can run `schtasks /Query /TN <name>` directly. **Tested against the real tool, not a mock**: `tests/cli_smoke.rs::install_and_uninstall_schedule_round_trip_via_real_schtasks` does a genuine `--install-schedule` → `--uninstall-schedule` round trip against the actual Windows Task Scheduler (with a `Drop`-based best-effort cleanup guard in case an assertion panics mid-test), on top of unit tests covering the full parsing/argument-building/flag-stripping grammar.
- See `ANALYSIS.md` Parte 3 for the full post-5.1.0 defect list (D1-D10, all resolved except D10 which is instrumentation-only) and `ROADMAP.md` milestones 5.2.0/5.3.0 (both closed)/6.0.0 (F30/F31/F33/F34 — Full+Incremental+Differential — /F35/F36/F39 closed; F32, F37, F38, F40 open) for what is planned.

## 3. Communication & Tone Guidelines

- Keep responses concise and direct.
- Code comments and commit messages must be in **English**.
- Documentation files (`README.md`, `ARCHITECTURE.md`, `ANALYSIS.md`, `ROADMAP.md`) are written in **Italian**, as requested by the project maintainers.

## 2. Key Architecture Concepts for Claude

When editing or extending `robocopy-ingest-cli`, keep these design patterns in mind:

### Robocopy Process Execution:
- The actual execution goes through the `CommandRunner` trait (`src/engine/robocopy.rs`).
- `ProcessRunner` is used on Windows (`#[cfg(windows)]`), while `ScriptedRunner` is used in unit tests on all OSes.
- Never modify Robocopy flag building without updating the corresponding unit tests in `robocopy::tests`.

### Memory Safety & Anti-OOM Controls:
- **Logging**: Uses `tokio::sync::mpsc::channel(10_000)` with `try_send`. Never switch back to an `unbounded_channel`.
- **Integrity Report Capping**: `IntegrityCheck` caps error vectors at `MAX_REPORTED_ERRORS = 10_000`.

### CLI Argument Rules:
- All CLI flags defined in `src/cli.rs` must also support optional TOML config overrides via `src/config.rs` (`IngestConfig`). `merge_config` only overwrites a field when the CLI still holds clap's own default for it (see the comment in `Args::merge_config`); it cannot yet distinguish "explicit CLI value equal to the default" from "no CLI value at all" (would need `ArgMatches::value_source`).
- Paths should be normalized via `normalize_path_arg` to handle Windows backslashes correctly.
- Default pattern is `*` for full recursive copy. `--mirror` mode runs `check_mirror_safety` in `main.rs`, which diffs the destination tree against the source inventory and aborts (dedicated exit code 3) unless `--force-purge` is given or the run is interactive and the operator confirms. This only works when a full prescan was taken; `--no-prescan` + `--mirror` always requires `--force-purge`.
- Stdout/stderr decoding uses `src/oem_codec.rs` (a hardcoded CP850 table plus a `GetOEMCP()` runtime check), **not** `encoding_rs::Encoding::for_label(b"ibm850")` — `encoding_rs` does not implement single-byte DOS/OEM code pages, so `for_label(b"ibm850")` always returns `None` and silently falls back to UTF-8. Do not reintroduce that pattern.
- `--enable-dedup`, `--cloud-sync-target` are accepted for forward compatibility but are **not implemented** (see `[NOT IMPLEMENTED]` markers in `src/cli.rs`). Don't describe these as working features in docs. `--install-service` **is now implemented** (F37) — see the dedicated note below; don't confuse it with these two.
- `--ignore-transient-missing` (F26a, closes half of D2) **is implemented**: `integrity::ignore_transient_missing()` runs after `--verify-integrity` and drops `missing_in_dest`/`unreadable` entries matching well-known transient patterns (`.log`, `.tmp`, anything under `.git/objects/`), recomputing `status`. Has no effect without `--verify-integrity`. Do not confuse this with `--fast-verify` above — they're unrelated despite both touching the verification path.
- `--exclude-junctions` (F26d, closes D7) maps to robocopy's `/XJ` in `engine/robocopy.rs::build_args`. Without it, robocopy follows junction points/symlinked directories (its own default) — and so does the prescan: `scan::scan`/`scan::inventory`/`scan::directory_size` all take an explicit `follow_links: bool` parameter, driven from `!args.exclude_junctions` (or `!request.exclude_junctions` in the naive engine) at every call site in `main.rs`. Keep these two in sync — the whole point of the flag was that the prescan and the actual transfer used to walk different trees. `WalkDir` rejects cycles when following links, so a self-referencing junction errors per-entry instead of recursing forever.
- `--serve-dashboard` and its backing `src/server.rs` mock were **removed** (Release 5.4.0) in favor of the `notify-server` binary. Do not reintroduce a `--serve-dashboard` flag.
- `notify-server` (`crates/rustcopy-cli/src/notify_server_bin.rs`, `src/notify_server.rs`, `src/notify_sink.rs`) receives `--webhook-url` POSTs and fans them out to configurable channels. It is a **separate, feature-gated binary** (`--features notify-server`): axum must never become a default dependency of the main `robocopy_ingest` binary. `src/notify_sink.rs` (the `NotificationSink` trait and channel impls) has no axum dependency and is always compiled/tested; only `src/notify_server.rs` (the axum `Router`) and the bin are feature-gated.
- `--encrypt-aes256 <KEY>` / `--decrypt <KEY>` perform real streaming AES-256-GCM (see `src/crypto.rs`, fixed F25a/F25b, closes D3/D4). Encryption/decryption happen in fixed **1 MiB chunks** (`CryptoManager::encrypt_stream`/`decrypt_stream`), each with a fresh random nonce and an explicit length prefix — peak memory is O(chunk size), not O(file size), so this no longer OOMs on large files. On-disk format: `RCE1` magic header + repeated `nonce(12) || len(4, LE u32) || ciphertext+tag` records. `CryptoManager::encrypt_file`/`decrypt_file` write to a sibling temp file and `rename` atomically only on success — never leaves a half-transformed file at the real path. Both flags are mutually exclusive (`Args::validate()` rejects both being set, checked *before* the restore-mode early return since `--decrypt` is meant to be used with `--restore-from`). Do not reintroduce whole-file `std::fs::read`/`std::fs::write` for either direction.
- `--restore-from` is **fixed and verified (F24, closes D1)**: `--source`/`--dest` are now `Option<PathBuf>` with `required_unless_present = "restore_from"` (the previous `PathBuf` + `default_value = ""` combination silently made clap treat the arg as unconditionally required — an empty-string default is treated as "no default" by clap, so `required_unless_present` never took effect). Access them via `Args::source()`/`Args::dest()` (`&Path`, panics if called when neither was supplied — an invariant clap enforces before `validate()`/these accessors ever run in a real invocation), never the raw `Option` fields directly outside `cli.rs`. Covered by a black-box test that runs the compiled binary (`tests/cli_smoke.rs::restore_from_runs_end_to_end_without_source_or_dest`), not just `build_restore_args()` in isolation — the latter is exactly what let the original bug ship undetected.
- `restore::build_restore_args` takes the **original, already-parsed `Args`** for the current invocation and clones it, overriding only the fields that must come from the backup report (source/dest reversed, pattern, threads, retries, retry_wait_seconds, verify_integrity). Do not rewrite it to build a fresh `Args` via `try_parse_from` again — that was the F25b regression: every other flag typed alongside `--restore-from` (notably `--decrypt`, but also a custom `--log-path`/`--report-path`/`--webhook-url`) got silently discarded because `main.rs` replaces `args` wholesale with this function's return value. Caught only by a black-box test that combined `--restore-from` with `--decrypt` end-to-end, not by the pre-existing unit test (which never passed any extra flag).
- `check_mirror_safety` in `main.rs` is `async fn` (F26b, closes D5): the destination walk it does runs inside `tokio::task::spawn_blocking`, like every other blocking filesystem operation in that file (inventory, transfer, verify, crypto, the dest poller). Don't call it synchronously from `execute()` again — that's exactly the regression it fixed (froze the tokio executor, and `Ctrl+C` handling with it, for the whole scan on large trees).
- `report::SCHEMA_VERSION` is `2` (F26c, closes D6): bumped from `1` after a past release renamed `integrity::Mismatch`'s fields (`source_sha256`/`dest_sha256` → `kind`/`algorithm`/`source_digest`/`dest_digest`) without bumping it. Those four fields carry `#[serde(default)]` (with a dedicated `impl Default for MismatchKind`, documented as a deserialization fallback only) so a genuinely old-format report — which `restore::build_restore_args` parses in full — stays deserializable instead of failing `--restore-from` outright. `path` has no default; without it there's nothing to identify the entry by.
- `--log-level`/`--quiet`/`--log-max-bytes`/`--log-max-backups` (F27, closes D9) are implemented: `Args::log_config()` builds a `logging::LogConfig` (filter string + rotation settings) consumed by `logging::init`/`init_scoped`. `RUST_LOG` still wins over the CLI-derived filter, unchanged from before this existed. `logging::rotate_if_needed` still runs once at startup, before the log file is opened — D18 (see below) later added mid-run rotation on top of this, so rotation is no longer startup-only overall. `--quiet` and `--log-level` are `conflicts_with` each other in clap (mutually exclusive, not "one silently wins").
- `--fast-verify` (F28, closes the other half of D2) **is implemented**, but deliberately *not* the way the original ROADMAP wording described ("hash only files robocopy declares copied"): the robocopy stdout parser (`engine::robocopy::parse_file_bytes`) extracts byte counts per line, not filenames, and is already load-bearing for progress reporting — reworking it to expose per-file identity was judged materially riskier than the alternative actually implemented: `cache.rs`'s `IngestCache`, keyed on **source** file size+mtime, persisted at `<dest>/.ingest_cache` (`cache::default_cache_path`). A file is skipped only when its current size+mtime match the entry from the *last run that verified it clean* — a file that fails verification is never written to the cache, so it keeps being re-checked every subsequent run until it actually passes (see `main.rs::verify`'s `failed` set, computed *before* `--ignore-transient-missing` runs, so a forgiven transient-missing file still isn't wrongly cached as confirmed-present). Known limitation, documented in the flag's own help text: this trusts the *source*'s identity, not a re-check of the destination's bytes — independent destination corruption (e.g. bit rot) with an unchanged source will not be caught on a run where that file gets skipped. `IntegrityCheck::skipped_unchanged` reports how many files were skipped this way (`0` when `--fast-verify` isn't used).
- `IntegrityCheck::skipped_unchanged`, `ScannedFile::modified_timestamp`, `HashAlgorithm::Xxh3` and `EXIT_INTEGRITY_FAILED = 4` (F28/F29a/F29b) are all additions on top of the F26c-era shapes; none of them break deserialization of older reports (all `#[serde(default)]` where relevant).
- Exit codes (`main.rs`): `0` success, `1` the transfer itself failed (robocopy exhausted retries on some item), `2` usage/unrecoverable error, `3` `--mirror` purge aborted, `4` the transfer succeeded but `--verify-integrity` found a problem (F29b, distinguishes "data never landed" from "data landed but doesn't match" for schedulers), `5` `--keep-generations` retention purge aborted (F35 — kept distinct from `3` so a scheduler can tell a mirror-purge abort from a retention-purge abort). `run()` in `main.rs` returns the exit code (`u8`) directly rather than a `bool`; `RunOutcome::exit_code` is computed once in `execute()`.
- `--hash-algo` has a third option, `xxh3` (F29a, via the `xxhash-rust` crate). It is **not cryptographic** — good for corruption detection, not for a backup where an attacker could have tampered with data. Don't recommend it for that use case in docs or generated summaries.
- `engine::CopyRequestBuilder`/`CopyRequest::builder()`, `IngestError::IntegrityFailed`, and `report::seconds()` were **removed** (F29c, closes D8) — they had zero callers. Do not reintroduce a builder pattern for `CopyRequest` without a real caller driving the requirement.
- `--vss-snapshot` (F30, closes O1) shells out to `vssadmin.exe` (`src/vss.rs`) rather than binding the VSS COM API directly — matches how the rest of the crate delegates to native tools instead of pulling in a COM/FFI dependency. `main.rs`'s `VssGuard` holds the shadow copy for the run and deletes it in a **synchronous `Drop`**, deliberately not an async cleanup step: `run()`'s `tokio::select!` drops `execute()`'s future outright on Ctrl+C instead of driving it to completion, and a `Drop` impl on a value still living in that future's local scope is the only thing guaranteed to still run when that happens. Never move a `VssGuard` into a `spawn_blocking` closure — that would detach it from the future and defeat this. Requires Administrator; fails clearly, never falls back to reading the live volume silently. `inventory_source`/`transfer`/`baseline`/`verify` all take an `effective_source: &Path` parameter (the shadow-remapped path when `--vss-snapshot` is active, `args.source()` otherwise) — `args` itself is never mutated, so the JSON report still shows the real source path. **Not tested end-to-end**: creating/deleting a real shadow copy needs real Administrator elevation and touches real system state, outside every other test's `tempdir`-only sandbox — only the pure parsing/path-remapping logic in `vss.rs` is unit-tested (6 tests, against real captured `vssadmin` output).
- `--resume-from <checkpoint>` (F31, closes O5) is **not** mid-file resume — `engine::robocopy::build_args` still never passes `/Z`, deliberately, for its throughput cost on small files (see the `/Z` note above). It relies on robocopy's own default of skipping a destination file whose size+timestamp already match the source. What it actually adds: `run()`'s `Ctrl+C` branch now writes a `checkpoint::Checkpoint` to `<report_path>.checkpoint.json` before returning (previously wrote nothing at all), and `checkpoint::build_resume_args` reconstructs `Args` from it the same way `restore::build_restore_args` does — clone the **original, already-parsed** `Args` for this invocation and override only source/dest/pattern/threads/retries/retry_wait_seconds/verify_integrity, so every other flag typed alongside `--resume-from` survives. Unlike `--restore-from`, source/dest are **not** reversed. `--restore-from` and `--resume-from` are `conflicts_with` each other in clap.
- `[[jobs]]` in the TOML config (F33, closes O10) lets one config file describe several independent backup jobs — full schema and merge semantics in `ROADMAP.md`'s F33 row. `main.rs::run_jobs` rebuilds each job's `Args` from a fresh clone of the **original** CLI invocation, never the previous job's already-merged `Args` — do not rewrite it to build a fresh `Args` via `try_parse_from` again (see the F25b note above for why that silently drops flags). All jobs share **one** log file (`logging::init` only installs the subscriber on its first call per process). Each job still gets its own report: `main.rs::namespaced_path` inserts `.{job_name}` before the extension unless the job's **own** `JobConfig.report_path` is set — check that field directly (`is_none()`), not the already-`merged_over`-resolved one, which always looks "set" once the file has a top-level default.
- `--backup-type <full|incremental|differential>` (F34, closes Cobian parity's central gap) is implemented in `src/generations.rs` + `main.rs::execute_generation_backup`, opt-in only — `None` is the exact pre-F34 behavior. Full diff-logic detail (chaining, `latest()` vs `latest_full()`, manifest shape) in `ROADMAP.md`'s F34 row. `Args::validate()` rejects `--backup-type` together with `--mirror` (`IngestError::BackupTypeAndMirrorConflict`) — `/MIR`'s purge semantics have no meaning against a manifest-based multi-generation destination. Incremental/differential copies do **not** go through `transfer()`/robocopy (see `AGENTS.md` rule 9 for why) — `engine::naive::copy_selected` does the actual copy for all three types, sharing the per-file streaming `copy_one` with the plain naive engine. **Scope not yet wired up**: `--compare-baseline`, `--verify-integrity`, encrypt/decrypt, and VSS remap of the destination side don't run inside `execute_generation_backup`.
- `--keep-generations <N>` (F35, closes retention/rotation) requires `--backup-type` (`IngestError::KeepGenerationsWithoutBackupType` otherwise). `GenerationManifest::cycles()` rotates by **cycle** (one `Full` plus every `Incremental`/`Differential` up to the next `Full`), not by raw generation — deliberate, see `ROADMAP.md`'s F35 row: pruning by raw generation could delete a `Full` still referenced by a kept incremental/differential, orphaning that chain. `main.rs::prune_old_generations` uses the same `--force-purge`/interactive-confirmation gate as `check_mirror_safety`; an aborted purge maps to dedicated exit code `5` (distinct from `--mirror`'s `3`, so a scheduler can tell which purge was aborted). Pruning runs *after* the new generation is copied and saved, so an aborted purge never loses the run's own backup. `keep_generations` has TOML parity in `JobConfig`; `force_purge` deliberately does **not** (same reasoning as the `--decrypt`/`--restore-from`/`--vss-snapshot`/`--resume-from` exceptions above — a purge-confirmation bypass shouldn't be config-settable).
- `--pre-command <CMD>`/`--post-command <CMD>` (F39, closes Cobian's "events" parity) run via `cmd /C` (Windows) / `sh -c` (elsewhere) in `src/hooks.rs` — deliberately cross-platform so `hooks.rs`'s unit tests run on every CI platform. `run_pre_command` runs at the very top of `execute()`, **before** the VSS snapshot (F30) — a pre-command's typical job is stopping a database for consistency, which must happen before a snapshot is taken — and a failure is fatal (`IngestError::PreCommandFailed`, exit code 2): proceeding would silently back up inconsistent data. `run_post_command` runs after the backup has already succeeded, in both pipelines; a failure here is **not** fatal (mirrors the `webhook_error` pattern) — only logged and recorded in `IngestReport::post_command_error`. Both commands are plain, verbatim strings — same trust boundary as `--webhook-url`, no escaping/sandboxing. Both call sites use `spawn_blocking_with_span` like every other blocking op in `main.rs`.
- `--install-schedule <SPEC>`/`--schedule-name <NAME>`/`--uninstall-schedule <NAME>` (F36, closes scheduler parity) are implemented in `src/schedule.rs`, shelling to `schtasks.exe` — same "delegate to a native tool" pattern as `vss.rs`/`vssadmin.exe` (F30). `SPEC` grammar (`daily@HH:MM`/`hourly@N`/`weekly@DAY,...@HH:MM`) and the full architecture rationale are in `ROADMAP.md`'s F36 row. The command Task Scheduler runs (`/TR`) is built from the **real** `std::env::args()` of the current invocation, not a synthetic re-serialization of `Args` — `strip_schedule_flags` removes only the three scheduling flags themselves, so whatever else was typed alongside `--install-schedule` (including `--config job.toml`) survives verbatim into the scheduled command. `--uninstall-schedule` is exempted from `--source`/`--dest`'s `required_unless_present_any` and intercepted at the very top of `main.rs::run()`. `--install-schedule`/`--uninstall-schedule`/`--restore-from`/`--resume-from` are pairwise `conflicts_with_all` in clap. **Known gap**: no `--list-schedules` — the operator can run `schtasks /Query /TN <name>` directly. Tested against the real tool: `tests/cli_smoke.rs::install_and_uninstall_schedule_round_trip_via_real_schtasks`.
- `--install-service`/`--uninstall-service` (F37, closes the mock in `service.rs`) shell out to the real Windows Service Control Manager via the `windows-service` crate (platform-gated `[target.'cfg(windows)'.dependencies]`, not feature-gated). Full rationale in `ROADMAP.md`'s F37 row. Deliberately minimal scope: once installed and started, the service is **idle** — registers a control handler, reports `Running`, does nothing else until `Stop`; see `AGENTS.md` rule 13 for why `main()` in both `robocopy_ingest` and `notify-server` had to become a plain `fn` that checks `service::is_service_launch()` **before** building any tokio runtime — never move that check after runtime construction. `--install-service`/`--uninstall-service` don't require `--source`/`--dest` and are intercepted at the very top of `main.rs::run()`. Installed with `ServiceStartType::OnDemand`, not `Automatic`. Requires Administrator; `ServiceManager::local_computer(...)` returns its own access-denied error rather than this module pre-checking elevation. **Untested end-to-end**, same declared limitation as `--vss-snapshot` (F30): a real `CreateService`/`StartService`/`DeleteService` round trip needs genuine Administrator elevation and mutates real machine state — only `service::service_binary_path`/`service::is_service_launch` have unit tests; the real round trip was verified manually.
- `notify-server` (F41, closes persistent-service parity) gets its **own** Windows service identity (`"RustcopyNotifyServer"`), separate from `robocopy_ingest`'s idle one (F37, `"RustcopyIngestService"`) — see `AGENTS.md` rule 14 for why (keeps rule 8's "notify-server stays feature-gated" intact). `service.rs`'s SCM plumbing was generalized into name-parameterized functions (`install_named`/`uninstall_named`/`start_dispatcher`/`register_and_wait_for_stop`) shared by both binaries; `service.rs` itself still has zero axum dependency — the axum-hosting service body lives entirely in `crates/rustcopy-cli/src/notify_server_bin.rs`, feature-gated. `notify-server`'s `main()` is also a plain `fn` per rule 13. The service body reconstructs `Args` via `Args::parse_from` from the real argv, then runs axum inside a `tokio::runtime::Runtime` built on the dispatcher's plain thread; SCM's `Stop` is bridged into axum's graceful shutdown via `notify_server::serve_until_shutdown_or` (the original `serve_until_shutdown` is untouched and still used by the normal foreground path). **Same untested-end-to-end limitation as F37/F30**: covered by black-box tests that the clap conflict is rejected and both commands fail cleanly without elevation, not a real `CreateService`/`DeleteService` round trip. Full detail in `ROADMAP.md`'s F41 row.
- `scan::scan`/`scan::inventory` (D11, fixed 5 Agosto 2026, see `ANALYSIS.md`'s D11 section) now take `exclude_dirs: &[String], exclude_files: &[String]` and prune matching subtrees via `WalkDir::filter_entry()` instead of walking the whole tree and filtering after the fact. Before this fix, `exclude_dirs`/`exclude_files` only ever reached `engine/robocopy.rs::build_args`'s `/XD`/`/XF` for the real robocopy transfer — the prescan, the `naive` engine, and the post-`CopyFailed` reconciliation scan all ignored both flags. All three call sites in `main.rs` (`inventory_source`, `check_mirror_safety`, the reconciliation scan) now thread `args.exclude_dirs`/`args.exclude_files` through — `check_mirror_safety`'s destination-side scan needs the same exclusions applied so it compares like-for-like trees against `/MIR`'s own `/XD`/`/XF` behavior.
- `scan::scan`/`scan::inventory` also now take `min_age_days`/`max_age_days: Option<u32>` (D17, fixed 21 Agosto 2026, see `ANALYSIS.md`'s D17 section) — the same D11-shaped gap, now closed for age too. `fails_age_filter` implements the real `robocopy.exe` semantics, verified empirically against the binary (not assumed): `/MINAGE:N` excludes files modified **less** than N days ago, `/MAXAGE:N` excludes files modified **more** than N days ago — the opposite of what `--min-age-days`/`--max-age-days`'s own `--help` text said before this fix. Threaded into `inventory_source`/`check_mirror_safety` (same reasoning as D11) but deliberately **not** the post-`CopyFailed` reconciliation scan, which counts what is actually on disk right now, not a source-side selection decision. `engine::naive::NaiveCopyEngine::copy` (used by `--compare-baseline`) also got this fix — `CopyRequest` already carried the two fields, `engine/robocopy.rs::build_args` already used them for the real transfer, but this engine's own scan never threaded them through.
- `logging::DEFAULT_FILTER`/`cli::LogLevel::default()` (D18, fixed 22 Agosto 2026, see `ANALYSIS.md`'s D18 section) changed from `debug` to `info` — `debug` emits one line per file copied, measured at 356 MB on a real 1.34M-file run (`_ops_reports/full-profile-test.log`), 76x larger than the same run at `info`. `--log-max-bytes` (`logging::build`'s writer task) now also rotates **mid-run**, not just at the previous process's startup: it tracks cumulative bytes written (seeded from the post-startup-rotation file size, not zero) and on crossing the threshold does `flush` → `tokio::fs::File::into_std().await` (waits out in-flight ops, then `Drop`s the returned `std::fs::File` to close the OS handle synchronously — Rust's default `FILE_SHARE_DELETE` on Windows would likely permit renaming the still-open handle anyway, but this removes the doubt) → the same tested `rotate_if_needed` → reopen fresh. Do not add a rotation check anywhere except right after a `LogMessage::Line` write — `Flush`/`Stop` never grow the file. Any test that pins a small `--log-max-bytes` alongside real log output must leave enough headroom above one formatted line's size, or the run's own output re-triggers a second rotation and overwrites the seeded content the test meant to check (hit this project's own tests here, twice, while writing this fix).
- `cache::default_cache_path` and `generations::GenerationManifest::path_for`/`load_or_default`/`save` (D12, fixed 6 Agosto 2026, see `ANALYSIS.md`'s D12 section) now take a `job_name: Option<&str>` that namespaces the filename via `robocopy_ingest::namespaced_path` (moved from `main.rs` into `lib.rs` so `cache.rs`/`generations.rs` can reuse it). Before this fix, `.ingest_cache` and `.rustcopy_generations.json` were derived **only** from `dest`, unlike `report_path` (already namespaced per job by F33) — two jobs in the same `[[jobs]]` batch sharing a `dest` with `--backup-type` could merge generation histories, letting `--keep-generations` prune a still-needed `Full` generation from a different job's chain. `Args::job_name: Option<String>` (`#[arg(skip)]`, never a real flag) is set unconditionally by `run_jobs`. `None` (single-job path) is unaffected.
- `main.rs::spawn_blocking_with_span` (D13, fixed 6 Agosto 2026, see `ANALYSIS.md`'s D13 section) is a drop-in replacement for `tokio::task::spawn_blocking` that captures `tracing::Span::current()` before handing the closure to the blocking-pool thread and re-enters it there — a plain `spawn_blocking` closure does **not** inherit the calling task's active span, so without this every log line from a blocking closure would silently drop out of `run_jobs`'s (F33) per-job `tracing::info_span!("job", job = %job_name)` context. **Do not add a new `tokio::task::spawn_blocking` call site in `main.rs` without going through `spawn_blocking_with_span`** — every blocking call in this file must stay reachable from within a job's span in a multi-job batch.
- `robocopy_ingest::atomic_write` (`lib.rs`, D14) writes via a same-directory sibling temp file (`<path>.rustcopy-tmp`) plus rename — same safety property as `crypto.rs`'s `encrypt_file`/`decrypt_file` (D3/D4), generalized for plain byte writes. `generations::GenerationManifest::save` and `cache::IngestCache::save_to` both go through it instead of a bare `std::fs::write`. Why this matters at this crate's scale: a `GenerationManifest` for the real-world 1.34M-file profile in `_ops_reports/full-profile-test.json` serializes to ~174 MB for **one** generation (measured empirically, see the `#[ignore]`d `generations::tests::probe_manifest_size_at_real_world_scale`), growing linearly with every generation kept before `--keep-generations` rotates it away — and unlike the fast-verify cache (whose `load_from` silently falls back to empty on a parse error), a corrupt manifest is **fatal**: `load_or_default`'s parse error propagates with `?` and aborts the whole job (`main.rs::execute_generation_backup`), permanently breaking every future incremental/differential/retention run against that destination until an operator manually intervenes. **Do not reintroduce a bare `std::fs::write`/`fs::write` for either of these files** — go through `atomic_write`.
- `main.rs::execute_generation_backup`'s copy failure handling (D15): a failure from `engine::naive::copy_selected` is caught explicitly (not propagated with `?`) and mapped to `EXIT_INGESTION_PROBLEM` (1), matching the plain-sync pipeline's `transfer()` failure semantics (F29b) — before this, it propagated fatally to `async_main()`, which mapped it to `EXIT_UNRECOVERABLE` (2), the same code used for a usage/config error, giving a scheduler no way to distinguish "the copy itself failed" from "you passed a bad flag." A JSON report is now always written on this path too (previously none was), carrying the new `IngestReport::copy_error: Option<String>` field — populated **only** by this pipeline; the plain-sync pipeline doesn't need it since its `TransferReport` already carries partial per-file stats even on failure. **Deliberately not fixed as part of this**: `engine::naive::copy_files` still aborts its entire loop on the first failing file with no partial `CopyOutcome` at all — the generation pipeline's failure report can't yet say how many files actually made it to disk before the failure, only that it failed (decided via `AskUserQuestion`; fixing that would mean changing the naive engine itself, also shared by `--compare-baseline`). A failed generation is still never pushed to the manifest (existing guard, now also gated on `copy_error.is_none()`).
- `.github/workflows/security-audit.yml` (added 23 Agosto 2026) runs `rustsec/audit-check`, in two separate jobs by trigger. Do not merge them back into one: `permissions:` is per-job, and only the scheduled run may hold `issues: write` — a shared job would hand that to same-repo pull request runs too, which don't need it and shouldn't have it.
- Every `cargo` invocation in `ci.yml` carries `--locked` (added 25 Agosto 2026). **Do not drop it to make a red job green**: `--locked` fails when the lockfile would need changing, which is precisely how a PR that edits `Cargo.toml`'s dependencies without committing the regenerated `Cargo.lock` gets caught. A failure here means the branch, not the flag, is out of sync.
- `ci.yml`'s `concurrency` group cancels superseded runs, but is gated on `github.ref != 'refs/heads/main'` — **`main` is deliberately exempt**: a push there is a merge whose result is worth recording even when another lands right behind it. `security-audit.yml` has no `concurrency` group at all, also deliberately: its cron and its push trigger don't compete, and cancelling a scheduled run would drop that week's only advisory check. Both workflows set `timeout-minutes` on every job (a hung job otherwise runs to GitHub's 6-hour default) — not hypothetical here, since the black-box tests drive real `robocopy.exe` child processes and stdout/stderr pipe deadlock is one of the failure modes this crate exists to solve.
- `.github/workflows/ci.yml` (added 6 Agosto 2026) runs `cargo fmt --check`, `cargo clippy -D warnings`, and `cargo test` on both `windows-latest` and `ubuntu-latest`, for both the default and `notify-server` feature sets — this repo's first-ever CI, and the first time the suite had ever actually run on Linux rather than just being assumed compatible by design. It immediately found D16: a real bug in `vss::remap_to_shadow` (built its result via `PathBuf::push`, whose separator behavior depends on the *host* platform rather than the Windows device-path semantics the function's output represents) plus several tests that were stale or missing a `#[cfg(windows)]` gate they needed. **Any new `tokio::task::spawn_blocking`-adjacent or path-building pure function shared across platforms should build its result via explicit string logic, not `Path`/`PathBuf` methods, if the value it represents only makes sense under one platform's path semantics** — `Path`/`PathBuf` behavior itself is host-platform-dependent, not target-semantics-dependent.
- 13 `.md` files (11 root + `docs/archive/PIANO_NOTIFY_SERVER.md`/`AGENT_HARNESS_PLAN.md`) carry minimal [OKF](https://github.com/W4G1/okf) v0.2 frontmatter (`type`/`title`/`description`/`status`/`generated`, `verified` only where actually checked), plus three generated bundle indexes (`index.md`, `docs/index.md`, `docs/archive/index.md`). Full rationale in `AGENTS.md` rule 15. **All OKF work goes through `scripts/okf-docs.sh`** — `index` regenerates the indexes, `check` runs every gate — and it holds the single definition of the tracked-docs list; do not re-inline that list into `ci.yml` or a second script. `generated`/`verified` are provenance stamps, not "last edited": don't bump `generated.at` on routine edits; do bump `verified.at` when a rewrite is substantial enough that the old attestation no longer covers the new content. An `index.md` declares **only** `okf_version` (§12) and is not a concept — never give it `type`/`title`/`description`. Adding a permanent doc: add the frontmatter, append it to `TRACKED_DOCS` in `scripts/okf-docs.sh`, run `scripts/okf-docs.sh index`, commit the regenerated indexes — CI fails on any of these being skipped.
- `IngestReport::previous_run_comparison` (`report.rs`, P2, full detail in `PIANO_MIGLIORAMENTI.md`'s P1/P2 implementation section) is populated by `report::read_previous_report(&args.report_path)`, called in `main.rs` **immediately before** `report.write_to(&args.report_path)` at both write sites — ordering is load-bearing: read must happen before that exact path gets overwritten. "The previous run" means whatever JSON was already at this exact path, not a directory scan — with `{timestamp}` templating (P1) every run gets its own path, so comparison is always `None`. `read_previous_report` mirrors `IngestCache::load_from`'s "silently fall back to `None` on a parse error" pattern, and is called via `spawn_blocking_with_span` like every other blocking read in `main.rs`. `RunComparison::throughput_mbps_delta_percent` is `None` (not `0.0`/`Infinity`) when the previous run's throughput was `0.0`. **Known limitation, not fixed**: no locking between this read and the later `write_to` — two processes racing on the same fixed path could read/overwrite each other's report; worst case is a wrong comparison field, never backup data.
- `robocopy_ingest::resolve_report_path_timestamp` (`lib.rs`, P1, full detail in `PIANO_MIGLIORAMENTI.md`'s P1 implementation section) replaces the literal `{timestamp}` in `--report-path` with this run's start time. Called right before `validate()`, once in `run()` and once per job inside `run_jobs`'s loop (its own fresh `chrono::Utc::now()` each time, not one shared across the batch). Within `run_jobs`, F33's `namespaced_path` actually runs *before* P1's resolution — but the order doesn't matter for the result (verified: `timestamp_placeholder_composes_with_per_job_namespacing` in `tests/cli_smoke.rs`), since they touch disjoint parts of the filename. A path with no placeholder is returned byte-for-byte unchanged, which is the case P2's `previous_run_comparison` depends on. `--install-schedule`'s argv snapshot is unaffected: it captures the raw invocation text, so a scheduled command still contains the literal `--report-path report-{timestamp}.json` and gets a fresh timestamp resolved on every future scheduled run, never frozen at install time.
- `GenerationManifest::append_generation` (D19, closes the write-cost half of the debt D14 documented) writes one compact NDJSON line per generation instead of `GenerationManifest::save` rewriting the whole file — `main.rs::execute_generation_backup`'s common-case call site uses this now; `save` (same signature, its serialization is now NDJSON too) still handles the one case that genuinely needs a full rewrite: `--keep-generations` pruning, which removes entries from the middle of the history. `append_generation` checks first (`is_legacy_format`, a cheap first-line-only peek) whether an existing file predates D19 and, if so, loads it fully and migrates via `save` instead of appending a raw NDJSON line — appending blindly to a pre-D19 file leaves it unparseable by either format (caught by CodeRabbit on this PR before merge: a real regression for any user upgrading with an existing manifest). `load_or_default` does the equivalent detection on the read side, and drops a torn trailing line (an append interrupted mid-write) with a warning rather than failing the whole load — a malformed line anywhere else is real corruption and fails loudly. **Do not reintroduce `push`+`save` for the common case**, and never add a legacy-append path that skips the `is_legacy_format` check.
- `GenerationManifest::load_or_default` (D20) is for the **one** caller that genuinely rewrites the whole file — `prune_old_generations`'s second load. Everyone else takes the streaming reader that matches what they actually need: `load_latest_generation`/`load_latest_full_generation` for a reference generation, `GenerationIndex::load` for retention's "which ids to prune" decision, and **nothing at all** for `--backup-type full`, which never reads the manifest. Loading the whole history costs memory that grows with every generation kept, unbounded, for data the caller discards. `GenerationManifest::cycles` and `GenerationIndex::generations_to_prune` must both keep going through the single `cycle_ranges` — **never** reimplement the cycle split separately, F35's "don't orphan an incremental by pruning its Full" safety argument rests on that one definition. Full detail, measurements and declared limits in `ANALYSIS.md`'s D20 section.
- `ScanSummary::files` is an `Arc<[ScannedFile]>`, not a `Vec` (D21). Every consumer must hand **owned** data to `spawn_blocking` while only ever reading it, so a `Vec` meant a real copy per hop — `verify` alone held four live copies of the whole inventory. Share it with `Arc::clone`; **never** `.to_vec()`/`.clone()` into a fresh `Vec` unless you are genuinely building a *different* list (the `--fast-verify` filtered subset is the one legitimate case). Read-only uses need no change: it derefs to `&[ScannedFile]`. Measurements and the declared limit in `ANALYSIS.md`'s D21 section.
- `src/history.rs` + `--advise` (`src/advise.rs`, Fasi 0/1 di `VALUTAZIONE_AI.md`) indicizzano una riga NDJSON per run conclusa. **L'indice vive accanto al report (`<report-dir>/.rustcopy_history.jsonl`), mai dentro `--dest`** — misurato: con l'indice in `--dest`, una sync ripetuta su albero immutato passava da 2 a 3 elementi copiati, perché scrivere nella destinazione ne cambia l'mtime e robocopy se ne accorge alla run dopo. `.ingest_cache`/`.rustcopy_generations.json` se lo permettono solo perché opt-in. ### Writing convention for this file (B5b, added 20 Agosto 2026)

A new feature/fix adds to `CLAUDE.md` **only** the operational prescription — what not to do and why, in one line. The full narrative — alternatives considered, test limitations, implementation history — goes in the corresponding row of `ROADMAP.md` (feature) or `ANALYSIS.md` (defect), which is already where the rest of the project looks for it. `CLAUDE.md` points there; it does not duplicate it.
